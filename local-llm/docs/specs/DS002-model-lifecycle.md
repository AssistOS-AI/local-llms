# DS002 Model Lifecycle

## Introduction

This specification defines how a model moves from a catalog entry to a running deployment and back, and what survives a restart. It reuses the catalog-plus-registry split of the retired repository DS008 ([at `03697765`](https://github.com/AssistOS-AI/local-llms/blob/03697765a35d92adf4c7db1be9616c0b5a64cb63/docs/specs/DS008-model-lifecycle.md)) and replaces its download and start rules.

## Core Content

### Catalog and registry

| Source | Where | Editable |
| --- | --- | --- |
| Seed catalog | `catalog/models.json`, schema `local-llm.catalog/v4` (`catalog/schema.json`); v3 remains readable under its original rules | No; ships with the agent |
| User registry | `state.registry` in `/data/state/controller.json` | Yes, through `local_llm_model_add`, `_update`, `_remove` |

Every entry is validated by `validateModel` (`src/controller/catalog.mjs`). Ids are 2–64 lowercase characters. Sources are keyed by weight format, not by runner: `gguf` is a Hugging Face source naming one `.gguf` file in an `owner/name` repository, or a split GGUF (below), `ollama` is an Ollama library tag, and `hf` (safetensors, read by vLLM) and `exl3` (EXL3, read by TabbyAPI) are Hugging Face snapshots (below). A `huggingface` or `hf-snapshot` source may name a Hugging Face-compatible mirror with `registry` (Hugging Face-compatible mirrors, below). A `gguf` source may instead be an `oci` source, and an `hf` source an `oci-snapshot` source, from an OCI registry (OCI registries, below). Every runner reads exactly one format (its adapter's `weightFormat`), so runners that read the same format share one download and one Delete weights. `recommended` and `validated` are keyed by hardware profile (`dedicated`, `unified`, `cpu`; DS005) and then by runner, because parameters and measurements are per runner and per kind of memory. `profiles` lists where a model is offered (every profile by default): the overview and Run see only the models of the agent's profile. `unified.envelope` is the unified profile's measured envelope (DS005); a model without one, bundled or added at run time, is sized by a labelled estimate there, not refused. The estimate reads `contextLength`, `memory.kvBytesPerToken` and `memory.layers` when the entry has them (the Add model form offers them, optionally) and names the ones it had to default. `mtp: true` declares that the weights carry a multi-token-prediction head, which MTP needs (DS005); it is a capability, not a measurement, so user entries may declare it, and a `recommended` MTP default requires it. A nonempty `unified.envelope` and nonempty `validated` labels are certifications: they come only from trusted inputs, the seed catalog or the operator's catalog, whose provenance is controlled outside the model-management API. `local_llm_model_add` and `_update` cannot self-certify an entry with them. The empty canonical forms, `unified: null` and `validated: {}`, certify nothing. Every trusted measured rectangle names its `loadMode` explicitly, and a mode it does not name is not covered. This specification approves no envelope values; the rules and the measurements are in [DS005](DS005-hardware-profiles.md). An Ollama source names a library tag. Seed Hugging Face sources must pin `commit`, `size` and `sha256`. User sources may name a branch; `model_add` resolves it to a commit, size and LFS sha256 through the Hugging Face API before the entry is stored. A user entry cannot reuse the id of any seed, whatever the profiles it is offered in, or of any stored entry, and an invalid stored entry is skipped rather than breaking the catalog. Delete weights finds any model's weights, including a model not offered in the current profile. Seed entries offered in the `cpu` profile are small GGUF models that fit a machine with a few GiB of free RAM (Qwen2.5 0.5B and 1.5B, Qwen3 4B Instruct 2507, all Q4_K_M and Apache-2.0), and gpt-oss-20b, which fits only a large host; `recommended.cpu` gives their llama.cpp defaults. The small ones are offered on every profile, so a GPU host runs them with the runner's own defaults for its profile. A stored user entry whose id equals a seed's is listed in `unsupportedModels` instead of being hidden silently: the seed takes the id, so the entry is not offered.

Earlier schemas are not migrated (catalog v3 dropped the v1 and v2 migration on purpose), and state this controller cannot read is reported, never misread. One change within v3 is applied once when the `cpu` profile arrives. A stored user entry that lists both GPU profiles (the old default, "every profile") also gets `cpu`. The state records `cpuProfileMigration`, so the change is not repeated. An entry that lists a single profile keeps it. Each changed entry is logged. A registry entry that is not valid v3 stays in the state file, is not offered, is listed with its reason in the overview's `unsupportedModels` and logged once at start, and can be removed with `local_llm_model_remove` (its downloaded weights, if any, stay on disk). Parameters saved for a model that no longer validate (another profile, a removed parameter) give way to the defaults, with one log line; a recorded deployment whose parameters no longer validate shows no context instead of an error. The state file stays at version 1; a state file of any other version is kept aside as `controller.json.unsupported-<time>` instead of being overwritten.

### Looking up a model before adding it

`local_llm_model_lookup` reads Hugging Face metadata for a repository at a revision, on huggingface.co or, with `registry`, in a Hugging Face-compatible mirror (below):

- the commit;
- whether the repository is gated, and its licence;
- every file of the requested format, with its size and digest.

For GGUF, split sets are grouped under their first shard. For `hf` and `exl3`, the snapshot's top-level files are listed, and sizing comes from the snapshot's `config.json` at the commit the lookup resolved, which is checked against the digest the repository listing gives for that file before it is read. Given one GGUF file, the lookup also reads that file's header with a ranged request. The request starts at the Hugging Face origin and follows redirects, and it stops once the header is parsed (at most 32 MiB). From the header it derives `contextLength`, `memory.layers`, `memory.kvBytesPerToken` (f16) and `architecture`.

The architecture name is the prefix of the header's own keys (`qwen2.block_count`, `gpt-oss.attention.head_count_kv`), so it may use lowercase letters, digits, underscore and hyphen (llama.cpp names include `gpt-oss`, `command-r` and `falcon-h1`), up to 40 characters, and no dot. A header that is well-formed but names no architecture, or one that cannot be used as a key prefix, is not an error: the lookup returns null sizing (`contextLength`, `memory.layers` and `memory.kvBytesPerToken` null, `architecture` `dense`) with a note, as it does for a hybrid, recurrent or latent-attention model whose KV size it cannot compute, and the estimate uses its defaults and says so. `invalid_gguf` is for a header that is malformed as GGUF.

It downloads no weights (tensor data) and writes nothing under /data. `HF_TOKEN` is sent only to the Hugging Face origin: every redirect is followed by the agent, which drops the token from a hop on another origin (the file host's CDN), and a next tree page named by a `Link` header on another origin is not followed; the lookup then fails with `lookup_failed`, reason `listing-incomplete`, instead of offering part of the listing. Every request goes through the network guard (below). The answer carries `registry: { id, kind, label }`. The Add model form uses the lookup so an admin picks a file instead of typing its name. The entry is then added with `local_llm_model_add` as before, recording `sizingSource`. While the form still names the repository, revision and file the lookup read, the entry's revision is the 40-hex commit the lookup resolved, so Add pins exactly the files whose sizing was shown even if the branch has moved since; a form edited to another repository, revision or file pins the revision as typed.

Values read from a header are unverified until the download is. After the controller's verified download, the header is read again from the verified file. The admissions that follow use those values, and any difference is logged. That applies to a GGUF entry whose `sizingSource` is `gguf-header`; sizing typed by hand (`manual`, or no `sizingSource`), a snapshot's `config.json` sizing and an Ollama tag are not read again, and neither is a catalog entry. A downloaded file whose header is malformed fails the Run with `invalid_gguf`, and one that cannot be read at all (an I/O error) with `sizing_unreadable`. A well-formed header whose architecture cannot be used (above) checks nothing: the stored, or defaulted, values stand, the log says so (and so does the admission warning on the `cpu` and `unified` profiles, which carry sizing warnings; the `dedicated` admission has none), and the Run goes on.

When the verified file changes the model's training context, the Run's parameters are worked out again from what the request asked for (and what an earlier Run had saved), not from the result already stored: a default `ctxSize` (the catalog's or the schema's) is capped at the verified context, so it is lowered when it was above it and no longer held down by a smaller stored context, and an explicit `ctxSize` above it fails with `invalid_params` after the download and before any runner starts. The estimate, the recorded parameters and the launch all carry that one value. Installing a model from the UI means adding it, then pressing Run, which downloads it with progress and a Cancel.

The lookup reads at most 50 tree pages, one level of subdirectories (32 of them) and 500 files, and says `truncated` when it stopped early. The header reader (`src/controller/ggufHeader.mjs`) treats the bytes as untrusted: version 2 or 3 only, at most 4,096 key-value pairs, 256-byte keys, 4 MiB strings, 4,000,000-entry arrays, nesting depth 2 and 32 MiB in all, with nothing allocated for a claimed length; numeric arrays of up to 4,096 entries are kept, at most 65,536 numbers across all of them, and longer or later arrays are skipped with their length; any violation, or a header that ends early, is `invalid_gguf`. A failed lookup is `invalid_request` (refused before any request), `not_found`, `access_denied` (401 or 403), `address_refused` (the network guard refused the address), `lookup_failed` or `invalid_gguf`; with a `registry`, also `registry_unknown` or `registry_disabled` (the registry, before any request), `internal_error` when the lookup was not given the guarded transport (the agent always gives it), and for an OCI registry `unsupported_artifact` (OCI registries, below). Hugging Face answers 401, not 404, for a repository that does not exist when no token is sent, so without a token the message says the repository was not found or needs access, and with one it says access was refused; both name `ploinky var HF_TOKEN <token>` and a restart. A model-info, revision or tree answer is taken from the Hugging Face origin only: a redirect of one of those requests to another origin is refused (`lookup_failed`), as a `Link` page on another origin is not followed; only a file read may be sent on to the file host's CDN. Each of those answers is read up to 8 MiB, and a larger one is `lookup_failed`. At most two lookups run at once, and a third is `busy`. A drain ends a lookup in flight with `shutting_down`.

On the `cpu` profile a user Ollama tag is pinned when it is added, because the CPU admission sizes a run from the pinned size. The agent reads the tag's manifest from `registry.ollama.ai` and records `manifestDigest` (the sha256 of the manifest bytes) and `size` (config plus layers, the Ollama store's own formula). The pull is then verified like a seed's, and the tag can be sized on the CPU. Only the manifest is fetched (at most 1 MiB, no credential, a redirect only within the registry's own origin). What the entry already carries is checked against the registry, not trusted: a digest or size that the registry no longer gives (a tag that moved, or a size typed wrong) is refused with `identity_changed` instead of being pinned, and one that is missing is filled in. A registry that cannot be reached, answers anything but a usable version 2 manifest, or has no such tag refuses the Add, so a tag is never stored unpinned by accident; a pin in flight ends as `shutting_down` when the agent drains. An Update that names a bare tag pins it afresh, which is how an entry stored before tags were pinned, or a tag that moved, is accepted. On the `dedicated` and `unified` profiles, and while the profile is undecided (an Add before anything has read the hardware), nothing is read and the tag is stored as typed, exactly as before: Add there needs no network, and Run checks a manifest digest only when the entry already carries one. A tag added before the `cpu` profile was decided has no size, and the CPU admission refuses it until an Update pins it. The registry's exact headers, and whether Ollama stores the manifest bytes it was sent (so that the stored file hashes to the pinned digest), are assumptions that a live pull confirms.

### Reusing a model file already in the workspace

**Trust model.** The agent's store (`/data`, on the host `<workspace>/.data/local-llm`) is written only by the agent and by the operator (the host user); its files and verification records are trusted at that level, and the records are a cache, not authentication. `/shared` is mounted read-write into every agent of the workspace, so everything in it is untrusted input: nothing read from it is used until a private copy of it has been verified. Hashing proves the bytes that were actually read. The stat identity recorded afterwards (device, inode, size, mtime, ctime) only detects accidental change; timestamps do not guarantee immutability, and a writer with operator access can still change a file after the last check, as it can a downloaded file.

**Where the agent looks, in order.** Before a controller download (a GGUF file, each shard of a split GGUF, each file of a Hugging Face snapshot):

1. **Its own store.** A file whose verification record matches the pinned identity is used as it is while its recorded stat is unchanged; a changed one is hashed again, kept if it still matches, otherwise removed and fetched again. A record without a stat is hashed once.
2. **In-place adoption.** A regular file already at the file's canonical store path, of the pinned size and with no valid record, is hashed and adopted where it is. This is the zero-copy path for a retained or separately downloaded file: the operator hard-links it on the host into the canonical path. The canonical paths are:
   - GGUF, and each shard of a split GGUF: `<workspace>/.data/local-llm/models/gguf/<owner>/<repo>/<commit>/<file>` (`<file>` is the file's whole path in the repository); - a Hugging Face snapshot file: `<workspace>/.data/local-llm/models/hf/<owner>/<repo>/<commit>/<file>`.

   The operator must not link a file that also stays under `.data/shared`: every agent could then write to it. The deployment log warns when an adopted file has other links.
3. **`/shared/models`** (on the host `<workspace>/.data/shared/models`; `LOCAL_LLM_SHARED_MODELS` overrides it for tests). A candidate is used only through a **private copy** into the store, hashed as it is written; it is never hard-linked (a link would share the inode with a path every agent can write, and inside the container `/shared` and `/data` are separate mounts, where `link()` fails with EXDEV anyway).
4. **The download** from Hugging Face, or its resume.

Only what the agent can see is searched: nothing outside the workspace, and Ollama tags keep Ollama's own store.

**Matching.** Only the pinned identity decides: the exact size and the pinned digest, the sha256 or, for a small file kept in git, the pinned git blob id. This holds for every shard and every snapshot file. Names only order the candidates.

**Binding verification to the bytes that were hashed.**
- **Anchored roots.** Every lookup root is anchored once per operation: its real path and directory identity (device and inode), never resolved again. The untrusted `/shared/models` root must itself be a directory, not a symbolic link, and must keep that identity at every candidate open: the root is opened as a directory (`O_DIRECTORY | O_NOFOLLOW`), its device and inode are checked on that descriptor, and the candidate is then looked up from that descriptor one directory at a time (through `/proc/self/fd/<root>/…`, as `openat` would), never through a link. A root substituted after its identity check therefore cannot supply the file; a root that moves while a candidate is opened makes that candidate unusable. Matching bytes do not waive this. The agent's own store root is trusted and may be a link the operator configured.
- **Opening.** A candidate or store file is opened with `O_NOFOLLOW | O_NONBLOCK`, so neither a final symbolic link nor a FIFO or device node can hold the open, and cancellation is checked around it. `fstat` must show a regular file before anything is read, and `/proc/self/fd` must show that the opened object is exactly the expected path under the anchored root, which also defeats a symbolic link in, or a swap of, any directory on the way (if that cannot be read, the agent fails closed).
- **Hashing.** The bytes are hashed through that descriptor, with an identical `fstat` before and after. A copy is hashed as it is written, and its source must not change while it is read. That digest proves only the bytes read from the source, not the bytes now in the staging file: once the copy is written and synced, the staging file is hashed again through its own descriptor, with an identical `fstat` before and after (the `verifying` phase). A staging file that does not match is `SHA256_MISMATCH`, one that changes while it is read back is `CHANGED_WHILE_VERIFYING`; either way the staging file is removed, any partial is kept, nothing is recorded, and no other candidate is tried.
- **Downloads and resumed prefixes.** A download's streamed digest only proves the bytes received. Before publication the finished partial, including a resumed prefix, is hashed again through its own descriptor with an identical `fstat` before and after; a change is `SHA256_MISMATCH` (the partial is removed) or, while it is being hashed, `CHANGED_WHILE_VERIFYING`. Nothing that changed during transfer or verification is recorded as verified.
- **Records.** The record keeps the identity of the object that was hashed: after the agent's own rename, the final path must hold the same device, inode, size and mtime (only ctime, which the rename changes, may differ). A copy is published while the descriptor it was read back through is still open: its full `fstat`, ctime included, must still be the verified one before the record is written and the file renamed (`CHANGED_WHILE_VERIFYING` otherwise).
- **Links in the store.** A symbolic link anywhere in the store is treated as absent and logged: at a file's path it is replaced by the fetched file (its target is never touched); in a directory on the way it refuses the Run with `UNSAFE_PATH`.
- **Directories.** The final, staging and record (`.state`) directories are created under the store root, refusing linked ancestors, before anything is placed or recorded, including the in-place adoption of a canonical snapshot that has no `.state` yet.

**Staging and resume.** Each candidate is copied to its own staging file (`<file>.partial.copy-<random>`, next to the partial). An existing `.partial` and its identity record stay untouched until a verified replacement is published; after a mismatch, an error or a Stop only the staging file is removed, and a later download resumes from the earlier offset. Staging files left by a crash are removed at the next attempt.

**A candidate never makes a resume impossible.** A `/shared` candidate is matched by size alone until it is hashed, so any file of the pinned size (even a sparse one that takes no disk) counts as one; its allocated blocks are not trusted to say otherwise. A partial counts when it is a regular file whose identity record matches and that is not longer than the pinned size; the overview, the plan and the transfer use this one rule. Beside such a partial holding at least one byte, the plan's method is `copy-or-resume` and the disk it needs is the resume's (`copyBytesNeeded` is the copy's): the transfer makes the copy only when the whole copy and its reserve fit, and otherwise leaves the candidate unread and resumes the partial in place, with one line in the deployment log. One free-space measurement per candidate, taken just before its copy would start, makes that choice and gives any refusal its figures, so two readings can never disagree. A copy that fitted by its measurement and then meets a full disk still pauses (`PAUSED_ENOSPC`, partial kept, below), and the next Run chooses again. Without a partial the plan is `copy` and needs the whole size.

**Copies follow the download's rules.** Free space for the copy plus the 5 % reserve is checked before copying (`INSUFFICIENT_SPACE` when there is no partial to resume instead). The copy runs in abortable chunks (8 MiB), so Stop, Cancel and drain settle within one chunk. Progress reports the `copying` phase, and hashing bytes already on disk reports the `verifying` phase. A full disk pauses the deployment (`PAUSED_ENOSPC`); other read and write errors fail it (`COPY_FAILED`); none is ever treated as "no candidate".

**Bounded, cancellable lookup.** One streaming walk of `/shared/models` per artifact (the overview uses one walk for every listed model) collects every size the artifact needs. It follows no directory link, stops at 8 levels and 20,000 entries, and checks for Stop before every directory it opens and at every entry. The Run's acquisition planning is cancellable too: Stop, Cancel and drain abort it before they queue behind the Run, so the walk ends once the pending read returns and the Run fails with `cancelled`. That holds whatever the walk found, including an empty or missing root: an aborted Run never reaches admission or creates a job. A Cancel that stopped the planning succeeds (the deployment is unchanged); a Cancel with no planning and no transfer is still `not_downloading`. At most 3 same-size candidates are hashed per file, those with the file's name first.

**Last check before loading.** Just before the runner starts, after any runner preparation, every file of the artifact is checked again: an unchanged stat, or its bytes are hashed again, shown as the `verifying` phase. A file that no longer matches fails the start (`CHANGED_AFTER_VERIFY`) before any runner is launched. This detects accidental change; it is not a lock.

**Provenance.** Every file and shard carries one shape, `{ file, source, method, bytes }`: `method` is `in-place`, `copy` or `download`; `source` is the store path, the `/shared` path or the download URL (never a token); `bytes` is what that way moved (0 in place, the size for a copy, the bytes transferred by that download). It is recorded with the file, returned by the fetch, stored as the deployment's `provenance`, and written to the deployment log, one line per file; a file that was already verified is logged as such with its recorded provenance. The Run's plan (`acquisition`: each file's method, `owned`, `in-place`, `copy`, `copy-or-resume` or `download`, and the disk it needs) is stored with the deployment when it is accepted.

**Delete weights** removes the agent's own files. `freedBytes` counts the logical size of each distinct inode (device and inode) whose last link the deletion removed; an inode that keeps a link outside the deletion set counts 0.

### Split GGUF

A large model can be published as a split GGUF: `<prefix>-00001-of-0000N.gguf` … `<prefix>-0000N-of-0000N.gguf` in one directory of the repository (Qwen3.5-122B-A10B MXFP4_MOE is three shards). It is still the `gguf` weight format, read by the same runners. The source's `file` is the first shard, which llama.cpp opens (it finds the others next to it), and `shards` lists every shard in canonical order, each pinned by `size` and `sha256`; `size` is their sum and there is no top-level `sha256`. A seed entry must pin every shard; a user entry may name only the first shard, and `local_llm_model_add` resolves the commit from it and every shard at that commit. Naming any other shard, or a split of more than 64 shards, is refused before anything is resolved.

The set is one artifact: one identity (commit, first shard, shard count) for in-use checks; its download state is complete only when every shard is, with bytes counted over the set; the download goes shard by shard into the one directory, each verified by its own sha256, with progress over the whole set; Delete weights removes every shard; and after the verified download every shard is dropped from the page cache.

### Weights on demand

Nothing is downloaded at enable, at restart, when the Local LLMs dashboard is opened, or when a model is added. Weights are fetched only by `local_llm_run`.

Each source type has a weight store (`src/controller/weightStores.mjs`) that pins, inspects, fetches and deletes it and names its artifact identity; runners that read the same file share that identity, so no runner may delete weights another runner is using.

| Format (source type) | Download |
| --- | --- |
| `gguf` (`huggingface`), fetched by the controller before the runner starts | `src/controller/downloader.mjs` fetches `/<repo>/resolve/<commit>/<file>` into `/data/models/gguf/<repo>/<commit>/<file>.partial` (the file's whole relative path, so same-named files in different folders never share a location), with an identity sidecar `<file>.partial.json`. It resumes with `Range`, restarts on a 200 reply, discards the partial on an invalid `Content-Range` or a changed identity, re-resolves expired redirects, refuses to start when free space is below the remaining bytes plus 5 %, pauses on `ENOSPC`, and renames the file into place only after the sha256 matches. |
| `ollama` (`ollama`), fetched by the runner | The Ollama adapter starts `ollama serve` with `OLLAMA_MODELS=/data/models/ollama` and streams `/api/pull`. When the entry pins `manifestDigest` (every seed, and every tag added on the `cpu` profile), the stored manifest must hash to it. |
| `gguf` (`oci`) and `hf` (`oci-snapshot`), fetched by the controller before the runner starts | Each file is an OCI blob, read from `<registry>/v2/<repository>/blobs/sha256:<hex>` through the registry's session with the same downloader (resume, free-space check, verification before the rename), into the `_oci` layout below. A layer's digest is the sha256 of the raw file, so the file is verified like any other. |
| `hf` and `exl3` (`hf-snapshot`), fetched by the controller before the runner starts | A snapshot is every top-level model file of a repository at one commit: names ending in `.json`, `.safetensors`, `.txt`, `.model`, `.tiktoken` or `.jinja`. It takes no subdirectories (gpt-oss-20b keeps a second copy of its weights in `original/`), no Python (remote code is never run), and no other weight formats. Each file is pinned by size and either its LFS sha256 or, for a small file kept in git, its git blob oid (sha1 over `blob <size>\0` and the bytes). `size` is the sum of the files. Seed entries pin every file; `model_add` pins a user entry's revision through the Hugging Face tree API. The files download one by one with the same downloader (resume, free-space check, verification before the rename) into `/data/models/hf/<repo>/<commit>/`. The partial files and identity records live in `/data/models/hf/.state/<repo>/<commit>/`, so the directory a runner loads holds only verified files. A snapshot is ready only when every file has verified. Delete weights removes the snapshot and its records together. |

`HF_TOKEN`, when set in the agent profile, is sent as a Bearer header to the Hugging Face base URL only and is never logged. The agent follows every redirect itself and drops `Authorization`, `Cookie` and `Proxy-Authorization` from a hop on another origin, so the signed CDN URL never receives the token.

Add and Update pin from metadata only. Each revision or tree answer is read up to 8 MiB (a larger one is `RESOLVE_FAILED`, reason `too-large`), a pin in flight ends when the agent drains (`shutting_down`), and a metadata request redirected to another origin is refused (`RESOLVE_FAILED`, reason `redirect`). A next tree page that is not followed (another origin, or outside the base URL's path) would pin an incomplete listing, so the GGUF pin and the snapshot pin both fail with `RESOLVE_FAILED`, reason `listing-incomplete`.

### Network guard

Every request a model path makes (the lookup, the pins and the controller's downloads of GGUF files, split shards and snapshot files) goes through one guarded transport, `src/controller/netGuard.mjs`. It contacts only globally routable addresses; nothing in the environment, the profile or a request can relax that, and the Hugging Face base URL is a code option only (there is no environment override). Runner downloads (DS004) and the Ollama runner's own pulls are outside it.

| Class | Refused |
| --- | --- |
| IPv4 | `0/8` (unspecified), `10/8`, `100.64/10`, `172.16/12`, `192.168/16` (private), `127/8` (loopback), `169.254.169.254` (metadata), `169.254/16` (link-local), `192.0.2/24`, `198.51.100/24`, `203.0.113/24` (documentation), `224/4` (multicast), `192.0.0/24`, `192.88.99/24`, `198.18/15`, `240/4` (reserved) |
| IPv6 | `::ffff:a.b.c.d` is judged as its IPv4 address. Everything outside `2000::/3` (`::1`, `::`, `fe80::/10`, `fc00::/7`, `ff00::/8`, `64:ff9b::/96`; `non-global-ipv6`), and inside it `2001:db8::/32` (documentation), `2001::/32`, `2001:2::/48`, `2001:20::/28` and `2002::/16` (reserved) |

| Rule | Detail |
| --- | --- |
| Where the address is checked | In the `lookup` hook the connection is made with: every resolved address is judged and only allowed ones are returned, so a socket can open only to an address the guard accepted, which is the DNS-rebinding defence. An IP-literal host (which skips DNS) is judged before connecting. The connected address is judged again before any request byte or credential is written. |
| Schemes | `https:` only (`RESOLVE_FAILED`, reason `scheme`); no userinfo in the URL. TLS verification is never disabled. |
| Redirects | Never followed by the transport. The agent follows at most 5 hops itself, each through the guard; https never steps down to http. |
| Encoding | Requests send `Accept-Encoding: identity`; an answer with another `Content-Encoding` is refused (`HTTP_ERROR`, reason `encoding`). |
| Timeouts | Response headers within 300 s; a body idle for 300 s ends the attempt. Metadata keeps its 15 s limit per request and the lookup its 55 s. |
| Connections | The transport owns its own HTTP and HTTPS agents (keep-alive), never the process-wide ones, so a pooled socket was always opened under this one policy. |
| Refusal | `ADDRESS_REFUSED` (Add, Update, and a Run, which fails with its message) or `address_refused` (lookup), not retried. The message names the host and the class (`<host> resolves to a <class> address, which local-llm does not contact`), never a resolved address, a token or a query. |

### Model registries

A registry is where a model source's files come from. Administrators define registries and their credentials with five admin tools (DS001), and edits apply without a restart. Because an administrator chooses the hosts, the network guard above is the safety boundary for them. The list is kept in `/data/state/registries.json`, `{ version: 1, registries: [ …administrator entries ], builtins: { dockerhub: { enabled }, ghcr: { enabled }, modelscope: { enabled } } }`, written atomically at mode 0600 in a 0700 directory (`src/controller/registries.mjs`). It is a separate file because the `controller.json` loader keeps only the keys it knows, so an older agent would erase a field stored there, and because a separate file stays out of the frequent progress saves. A missing file means the defaults. The file is rewritten on every edit and never deleted, so it stays even when it holds only the defaults. A file that cannot be parsed, or one of another version, is moved aside as `registries.json.corrupt-<time>` or `.unsupported-<time>` and the built-ins are used. An entry that fails validation (a manual edit) is not used and is logged once at start.

| id | kind | url | authOrigins | What an administrator may do |
| --- | --- | --- | --- | --- |
| `huggingface` | huggingface | `https://huggingface.co` | none | Nothing. It is always enabled, and its credential is the operator's `HF_TOKEN`. |
| `dockerhub` | oci | `https://registry-1.docker.io` | `https://auth.docker.io` | Enable or disable it, and set or clear its credential |
| `ghcr` | oci | `https://ghcr.io` | `https://ghcr.io` | Enable or disable it, and set or clear its credential |
| `modelscope` | modelscope | `https://www.modelscope.cn` | none | Enable or disable it, and set or clear its credential. It cannot be re-pointed; another ModelScope site is added under its own id. |

An administrator may add up to 32 entries, with these keys only:

| Key | Rule |
| --- | --- |
| `id` | `^[a-z0-9][a-z0-9-]{1,31}$`, unique. The built-in ids are reserved. |
| `kind` | `huggingface`, `oci` or `modelscope`. It never changes; a different kind is a new registry. |
| `url` | `https:` with a lowercase DNS host name and an optional port, and no user name, password, query or fragment. A host that is an IP address is refused when the registry is saved, after WHATWG normalization, so `https://2130706433`, `https://0x7f.1` and `https://127.1` (all `127.0.0.1`) are refused like `https://127.0.0.1`. A redirect to a literal address is still judged by the guard. A `huggingface` registry may have a path prefix of plain segments, at most 256 characters, with no `.`, `..` or empty segment; `oci` and `modelscope` registries are a bare origin. The URL must be written in its normal form (a trailing slash is allowed), so nothing typed is rewritten. It cannot change while a stored model entry or the running job uses the registry. |
| `label` | Plain text, at most 60 characters. The id when absent. |
| `enabled` | Boolean, true by default |
| `authOrigins` | `oci` only: 1–4 `https:` origins whose token realm may receive the credential. The registry's own origin when absent; while it is only that, it follows a change of `url`. |

Formats: `huggingface` and `modelscope` registries offer `gguf`, `hf` and `exl3`; `oci` registries offer `gguf` and `hf`. A source names its registry with `registry`; no `registry` means `huggingface`. A `huggingface` or `hf-snapshot` source may name a registry of kind `huggingface` (a mirror, below), and so may a lookup. A `modelscope` registry serves the same two source types (ModelScope, below). An `oci` registry serves `oci` and `oci-snapshot` sources and their lookups (OCI registries, below). `huggingface` and `modelscope` registries serve `huggingface` and `hf-snapshot` sources, and `oci` registries serve `oci` and `oci-snapshot` sources.

| Case | Rule |
| --- | --- |
| Edits | Every save, remove and credential change runs in the controller's command queue, so it never interleaves with an Add, Update or Run check. It changes the file first and then the in-memory list. |
| In use | A stored model entry, including one this catalog cannot read, and the deployment of the running job use the registries their sources name. While one does, a change of `url` or `kind` and a remove give `registry_in_use`, which names the models. |
| Built-ins | Saving `huggingface` gives `read_only`. Another built-in accepts only `id` and `enabled`; any other key gives `invalid_registry`. Removing a built-in gives `read_only`; disable it instead. |
| Disable | Allowed while the registry is in use. Add, Update and Run against it give `registry_disabled`. Delete weights, Remove, the overview and status still work. |
| Snapshots | A pin (Add or Update) resolves each source's registry once, at its start, into a frozen snapshot: the record and the credential decrypted then. Later edits apply to later operations. A lookup takes the snapshot at its start, and a download job when its fetch starts; each keeps that record and credential until it ends, whatever is edited meanwhile, and the next operation sees the edit. |
| Pin and queue re-check | Add and Update take the snapshot of every source's registry before they pin, and pin outside the command queue. Inside the queue block, before anything is saved, each registry must still exist, be enabled, and have the snapshot's `kind` and `url`. Otherwise the operation fails with `registry_unknown` (gone), `registry_disabled`, or `registry_changed` (kind or URL differ, for example a registry removed and re-created elsewhere during the pin), and `state.registry` is unchanged. |
| Kind mismatch | A source type the registry's kind cannot serve (an `oci` source naming a `modelscope` registry) is `invalid_model` at Add and Update, and `registry_changed` at Run for a stored entry. |
| Missing registry | Possible after a manual edit or a downgrade. Only the lookup, Add, Update and Run give `registry_unknown`. A store's paths, keys, state and Delete weights come from the source alone and never consult the list, so the overview still loads. |

### Hugging Face-compatible mirrors

A registry of kind `huggingface` other than the built-in one is a mirror: it serves the Hugging Face API and resolve URLs at its URL, under its path prefix if it has one. The lookup, the pins and the downloads are today's flow at that base URL (`src/controller/registryLookup.mjs` sends a lookup to the code for its registry's kind; `src/controller/registrySessions.mjs` builds the session a pin or a download uses).

| Rule | Detail |
| --- | --- |
| Source | `{ type: 'huggingface', registry?, repo, file, revision, … }` and `{ type: 'hf-snapshot', registry?, repo, revision, … }`. `registry` absent, or `huggingface`, is huggingface.co and is normalized away, so those entries and their records are unchanged. For any other id `revision` is required, because a mirror's default branch is not assumed (`invalid_model`). The id must match the registry id pattern. |
| Lookup input | `{ registry?, provider?, repo, revision?, format?, file? }`. `registry` is a registry id (the tool schema's pattern, at most 32 characters). `repo` is checked by the tool schema against the widest form any registry kind accepts (up to four segments, at most 255 characters), and by the code against `owner/name` for Hugging Face-compatible registries, so `a/b/c` is `invalid_request` before any request. `provider` may only be `huggingface`, and only with no registry or the `huggingface` registry. `registry` absent means `huggingface`. |
| Canary | Before a branch or tag is resolved, `GET <base>/api/models/<repo>/revision/local-llm-canary-<16 hex>` must answer 404. A 200 or any other unexpected answer is `lookup_failed` (`RESOLVE_FAILED` at a pin) with reason `nonconforming-registry`: a registry that answers a revision that cannot exist cannot be trusted to resolve one. A 401, 403, 429 or 5xx is that status's own error. The canary carries the credential the real request will. A 40-hex revision names itself and needs no canary. |
| Credential | The mirror's stored credential is sent as a Bearer header to the mirror's origin only, on metadata and on file requests. A hop to another origin (the CDN a resolve URL redirects to) never carries it, and a metadata request redirected off the origin is refused. A credential that is absent, or cannot be read with this agent's key, sends nothing. `HF_TOKEN` is sent to huggingface.co only and never to a mirror. |
| Listing | A next tree page on the mirror's origin and under its prefix is followed; a root-relative `/api/models/…` link is taken under the prefix. A next page anywhere else is not followed and the listing is incomplete: `lookup_failed` at a lookup and `RESOLVE_FAILED` at a pin, reason `listing-incomplete`, and the other origin receives no request. |
| Provenance | A downloaded file's provenance names the mirror's resolve URL with its prefix, never a CDN URL or a token. |
| Other kinds | A `huggingface` or `hf-snapshot` source naming a registry of kind `oci` is `invalid_model` (Kind mismatch, above); a source naming a missing or disabled registry keeps the `registry_unknown` and `registry_disabled` rules above. |

A mirror's files and identity keys live apart from huggingface.co's, under `_r/<id>`, and are derived from the source alone:

| Source | Files | Key |
| --- | --- | --- |
| huggingface.co GGUF (unchanged) | `models/gguf/<owner>/<repo>/<commit>/<file>` | `gguf:<repo>@<commit>/<file>[#n]` |
| huggingface.co snapshot (unchanged) | `models/hf/<owner>/<repo>/<commit>/`, `models/hf/.state/<owner>/<repo>/<commit>/` | `hf:<repo>@<commit>` |
| Mirror or ModelScope GGUF | `models/gguf/_r/<id>/<owner>/<repo>/<commit>/<file>` | `gguf:_r/<id>/<repo>@<commit>/<file>[#n]` |
| Mirror or ModelScope snapshot | `models/hf/_r/<id>/<owner>/<repo>/<commit>/`, `models/hf/.state/_r/<id>/<owner>/<repo>/<commit>/` | `hf:_r/<id>/<repo>@<commit>` |

`_r` cannot collide with a Hugging Face owner, which must start with an alphanumeric character. `registry` is part of the identity of a downloaded file's record, and is undefined for huggingface.co, so records written before registries existed are still current, without a request or a new hash. Delete weights of a mirror's model removes only its own files. The registry list is read by a lookup, a pin and a download only: a store's `key`, `state`, `plan`, `recheck`, `remove` and `paths` come from the source alone.

### ModelScope registries

A registry of kind `modelscope` (the built-in `modelscope` at `https://www.modelscope.cn`, or another site such as `https://www.modelscope.ai` added under its own id) serves `huggingface` and `hf-snapshot` sources from its own API (`src/controller/modelScope.mjs`). Commit ids are site-scoped, so a source records the registry id with its commit.

| Rule | Detail |
| --- | --- |
| Commit | `GET /api/v1/models/<repo>/commits?Ref=<revision>&PageNumber=1&PageSize=1` must give `Success === true` and a 40-hex `Commit[0].Id`, equal to the input when the input is 40-hex (the endpoint is asked for a commit too). `Commit: null` (or empty) is `not_found`; any other shape is `lookup_failed` with reason `nonconforming-registry`. A lookup without a revision uses `master`, ModelScope's default branch; a source always names its revision. |
| Listing | `GET /api/v1/models/<repo>/repo/files?Revision=<commit>&Recursive=true`. `Files: null` or empty is `not_found`. Only blobs count; an unsafe path (empty, dot or `..` segment, absolute, backslash, control character), a duplicated path (every copy), a size that is not a positive integer and a `Sha256` that is not 64 hex are skipped. Every file is pinned by size and sha256. |
| 3000 entries | The API cuts a listing at 3000 entries without a flag, so 3000 or more is `truncated: true` at a lookup (what was listed is still offered) and `RESOLVE_FAILED` with reason `listing-incomplete` at a pin. 2999 entries work. |
| Pin | GGUF: the file, or every shard of a split set, at the commit; a missing file or shard is `NOT_FOUND`. Snapshot: the top-level files a snapshot allows, with at least one `.safetensors`. |
| Gating and licence | `GET /openapi/v1/models/<repo>` is advisory: `gated` (`false`, or `manual` for `true`) and the licence are reported and never enforced. An answer that is missing, refused, too large, off-origin or not JSON leaves them `null`; a request that did not complete (a refused address, a network error, a timeout) fails the lookup. |
| Sizing | A ranged read of the GGUF's start on `/api/v1/models/<repo>/repo?Revision=<commit>&FilePath=<path>` (at most 32 MiB, as for Hugging Face), or `config.json` read whole from the same URL and checked against the listing's `Sha256`. |
| Download | Each file is read from the `/repo` URL above (the path is one encoded query value, so `/` is `%2F`), which may redirect to a signed CDN URL; it is verified against the pinned size and sha256 like any file. Provenance is the `/repo` URL, never the CDN URL. |
| Caps | Listing 4 MiB; commits and OpenAPI 1 MiB; a larger answer is `lookup_failed` with reason `too-large`. Requests ask for identity encoding; the guarded transport refuses an encoded answer. |
| Credential | `Authorization: Bearer <token>` to the registry's origin only, on metadata and on file requests. No cookie is sent, and a hop to another origin (the CDN) or a metadata redirect off the origin never carries it. `HF_TOKEN` is never sent to a ModelScope registry. |

### OCI registries

A registry of kind `oci` (the built-in `dockerhub` and `ghcr`, or one an administrator adds) serves GGUF files and CNCF per-file safetensors from OCI image manifests (`src/controller/ociSource.mjs`, `ociRegistry.mjs`, `ociStore.mjs`). Docker Hub serves two dialects, sometimes in one repository: the legacy Docker one (config `application/vnd.docker.ai.model.config.v0.1+json`, GGUF layers `application/vnd.docker.ai.gguf.v3` with no names) and CNCF ModelPack (`artifactType` `application/vnd.cncf.model.manifest.v1+json`, config `application/vnd.cncf.model.config.v1+json`, each file a `…weight.v1.raw` or `…weight.config.v1.raw` layer named by its `org.cncf.model.filepath` annotation). The dialect is read from the config media type, never from the tag.

| Rule | Detail |
| --- | --- |
| Sources | `{ type: 'oci', registry, repository, tag, manifestDigest?, layout?, file?, size?, sha256? \| shards?, quantization? }` (format `gguf`) and `{ type: 'oci-snapshot', registry, repository, tag, manifestDigest?, files?, size? }` (format `hf`). `registry` is required. `repository` is 2–4 lowercase segments, each `[a-z0-9]+` joined by `.`, `_`, `__` or dashes, with an explicit namespace (`library/x`), at most 255 characters. `tag` is `^[A-Za-z0-9_][A-Za-z0-9._-]{0,127}$`, `manifestDigest` `sha256:<64 hex>`. A pinned `oci` source has `manifestDigest`, `layout` (`docker` or `cncf`), `file`, `size` and `sha256`, or `shards` in canonical order; the `docker` layout's names are `model.gguf`, or `model-0000k-of-0000N.gguf` in layer order. A pinned `oci-snapshot` source has `manifestDigest` and 1–200 top-level model files (the snapshot rule above), each with `size` and `sha256`, at least one `.safetensors`; `size` is their sum. |
| Lookup input | `repo` is the repository and `revision` the tag (`latest` when absent). The formats are `gguf` and `hf`; `exl3` is `invalid_request`. The built-in registries' kinds are fixed, so their input is checked before anything else; an administrator's registry is checked by its kind once its snapshot is taken, and either way before any request. |
| Session | Each lookup, pin and download job has one session: its registry snapshot and one repository. A request goes to the registry origin, anonymously or with the cached bearer. A 401 is answered once per request. A `Bearer realm,service` challenge: the realm must be `https:` without user information, and its origin the registry origin or one of `authOrigins`, otherwise the request fails with `access_denied` at a lookup and `ACCESS_DENIED` at a pin or a download, "token realm not allowed", and the realm is never contacted. The realm URL is the realm with `service` and `scope` set through `URLSearchParams` (its own query is kept); the scope is `repository:<repository>:pull`, computed here, whatever the challenge named. The realm request goes through the guarded transport, follows redirects on the realm's origin only, and carries the credential as Basic (`tokenUsername:token`, with an empty user name when none is set) only when the realm's origin is in `authOrigins`. A `Basic` challenge gets the credential only when the registry origin itself is in `authOrigins` (an administrator's registry by default; not `dockerhub`, whose credential goes to `https://auth.docker.io` only). A challenge that is not one well-formed Bearer (with a realm) or Basic challenge is not answered: the 401 stands. |
| Token | The answer is read up to 64 KiB; its `token`, else `access_token`, must be 1–16 KiB of printable characters (`RESOLVE_FAILED`, reason `token`, otherwise). It is cached in the session for `min(expires_in or 60, 300) − 10` seconds and sent to the registry origin only, never to the realm, the CDN or another origin; a 401 with a cached token fetches a new one once. |
| Manifest | `HEAD /v2/<repository>/manifests/<tag>` gives `Docker-Content-Digest`; the manifest is then read by digest, and its body must hash to it (`SHA256_MISMATCH` at a pin, `lookup_failed` with reason `digest-mismatch` at a lookup), which also holds a digest the entry names. Without the header, the manifest is read by tag and its digest is the body's. Requests accept the OCI manifest and index and the Docker manifest and manifest list, so an index is answered as one and refused. A manifest is read up to 1 MiB (`lookup_failed` or `RESOLVE_FAILED`, reason `too-large`). Manifest requests are taken from the registry origin only. |
| Classification | Decided from the manifest alone, before any blob is read, so a refusal reads none. GGUF: the legacy `gguf.v3` layers in order (at most 64), or the CNCF `weight.v1.raw` layers whose filepath ends `.gguf` and whose base name does not contain `mmproj` (at most 64): single files, and split sets whose every shard is present, named in order and standing in layer order (a set out of layer order is refused, not reordered). Safetensors: CNCF `weight.v1.raw` and `weight.config.v1.raw` layers whose filepath passes the snapshot rule; `README.md` (a `doc.v1.raw` layer), `training_args.bin`, subdirectories such as `original/` and other names are dropped. A filepath is untrusted: an absolute one, a backslash, a control character or a `..` segment refuses the manifest; `.` and empty segments are dropped. At most 1024 layers. |
| Refusals | `unsupported_artifact`: an index or manifest list; an `artifactType` other than absent or the CNCF one (KitOps); a config type other than legacy v0.1 or CNCF v1 (v0.2 included); a layer whose media type is Ollama's, a tar (`vllm.config.tar`, `dir.tar`, `weight.v1.tar…`), or the legacy Docker safetensors or per-file layouts (`vnd.docker.ai.safetensors`, `vnd.docker.ai.model.file`); a CNCF config format other than `gguf` or `safetensors`, or not the requested one; duplicated filepaths; more than 64 GGUF layers or 1024 layers; no usable file; and a legacy split whose shard headers disagree with layer order. |
| Config | The CNCF config is read by its digest, at most 1 MiB, and must hash to it; its `config.format` must be the format asked for, and `descriptor.licenses[0]` is the lookup's licence. The legacy config is not read. |
| Pin | By `manifestDigest` when the source names one, otherwise by tag, then by digest. `oci`: the file is the one the source names (`NOT_FOUND` when the manifest does not offer it), or the only one offered (several give `invalid_model`, name one in `file`). A legacy split is checked at Add: each shard's own header must have `split.no` k−1 and `split.count` N. `oci-snapshot`: every file the classification keeps. Update keeps an `oci` pin while `registry`, `repository`, `tag` and `file` are unchanged and no other digest is named, and an `oci-snapshot` pin while `registry`, `repository` and `tag` are. |
| Lookup | The answer has the Hugging Face lookup's shape with `provider: 'oci'`, `commit: null`, `manifestDigest`, `layout`, `gated: null` and the licence. Sizing is a ranged read of the first shard blob's GGUF header (at most 32 MiB), or `config.json` read by its digest and checked. |
| Download | Each file is the blob of its sha256 at the registry origin, read through the job's session, which follows the redirect to the CDN with no credential and resumes with `Range`. Provenance is the registry's blob URL, never the CDN URL or a token. After a Run, the GGUF header of an `oci` file is read again as for Hugging Face (`sizingSource: 'gguf-header'`). |

OCI weights live under `_oci/<id>`. The digest is joined to the repository's last segment with `@`, which no repository segment can hold, so no OCI model's directory lies inside another's: `ns/m` at digest H and `ns/m/sha256-<hex of H>` at H2 never share a directory.

| Source | Files | Key |
| --- | --- | --- |
| OCI GGUF | `models/gguf/_oci/<id>/<repository…>@sha256-<hex>/<file>`, with the partial and records beside it as for GGUF | `gguf:_oci/<id>/<repository>@sha256:<hex>/<file>[#n]` |
| OCI snapshot | `models/hf/_oci/<id>/<repository…>@sha256-<hex>/`, `models/hf/.state/_oci/<id>/<repository…>@sha256-<hex>/` | `hf:_oci/<id>/<repository>@sha256:<hex>` |

A downloaded file's record holds `registry`, `repository`, `manifestDigest`, `file`, `size` and `sha256`. Paths, keys, state, plans, rechecks and Delete weights come from the source alone and never consult the registry list; only a pin and a download take the registry's snapshot. `/shared/models` adoption matches by size and sha256, as for any file.

Rollback: an agent older than OCI support hides `oci` and `oci-snapshot` entries (they are listed in `unsupportedModels`, kept raw and removable). If the last Run used an `oci` or `oci-snapshot` source, the older agent's Delete weights, Update and Remove of supported models fail with `invalid_model`, because it has no store for the deployment's artifact. The operator runs any huggingface.co model once after downgrading, before deleting anything; files under `models/{gguf,hf}/_oci/` are not reachable by the older agent's Delete weights and are removed by hand. `tests/fixtures/registry-rollback-base-check.mjs` rehearses this against the base agent.

### Registry credentials

| Item | Rule |
| --- | --- |
| Key | The manifest declares `LOCAL_LLM_CREDENTIALS_KEY` with `generatedSecret: true` (DS001). Ploinky derives it from the workspace master key and the agent's identity as 64 hex characters; it is recomputed at each start, never stored. Only exactly `^[0-9a-f]{64}$` is accepted. |
| Where the key goes | `src/agentProcess.mjs` reads the variable once, deletes it from the process environment before anything is spawned, and passes it explicitly to the controller and the registry service. No other code reads it from an environment. AgentServer, which gets a copy of the environment, and every child spawned without an explicit environment (such as `nvidia-smi`) therefore never receive it. The runner environment was already an allowlist without it or `HF_TOKEN`. |
| Derived keys | From the 32 bytes the key encodes: the AES key `HKDF-SHA256(salt '', info 'local-llm/registry-credentials/aes-256-gcm/v1', 32 bytes)` and the key id `HKDF-SHA256(salt '', info 'local-llm/registry-credentials/key-id/v1', 8 bytes)`, as hex |
| File | `/data/state/registry-credentials.json`, mode 0600 in a 0700 directory, written atomically: `{ version: 1, keyId, entries: { <id>: { keyId, iv, ciphertext, tag, updatedAt } } }`. Each entry is AES-256-GCM with a random 12-byte IV, base64. The plaintext is `{ token, username? }`. The entry's `keyId` names the key that sealed it; the file's names the key of the last write. Clearing the last credential rewrites the file with `entries: {}`; the file is never deleted. A file that cannot be parsed, or one of another version, is moved aside as `.corrupt-<time>` or `.unsupported-<time>`. |
| Binding | The GCM additional data is `local-llm/registry-credential/v1\n<id>\n<kind>\n<url>\n<sorted authOrigins joined by a space>`. A credential moved to another id, or read after its registry's URL changed by hand, fails the tag check. A save that changes `url` or `authOrigins` deletes the credential first, and so do removing a registry and adding one under an id that still has a stored entry. |
| Key absent or malformed | `local_llm_registry_credential_set` gives `credentials_unavailable` ("The agent did not receive LOCAL_LLM_CREDENTIALS_KEY; restart local-llm with a Ploinky that supplies generated secrets."). `local_llm_registry_list` reports `credentialStorage: { available: false, reason }`, and every stored entry reads `unreadable`, never `set`. Clearing still works. Requests go anonymously. |
| Key changed | An entry sealed under another key id, or one whose tag check fails, reads `unreadable`; requests through it go anonymously; and the agent logs one line per such registry at start, saying to re-enter it. Setting it again overwrites it under the current key. |
| States | `set` (it decrypts with this key for this exact registry), `none`, or `unreadable`. `huggingface` shows `set` when `HF_TOKEN` is set. |
| Use | A credential is decrypted for a snapshot (a lookup, a pin or a download job), held in that snapshot as a property that is not serialized, and decrypted and discarded at once when `local_llm_registry_list` and the start-up check tell `set` from `unreadable`. It is never cached across operations, and never written to state, provenance, the log, an error or a tool result. Error messages name a field, never its value. The token is 1–4096 characters with no control characters; `tokenUsername` is 1–256 printable characters with no colon, because the OCI Basic credential is `tokenUsername:token`. |
| Threat model | The encryption protects a copy of `<workspace>/.data/local-llm` made without `.ploinky/master-key`. It does not protect against the host user, who holds both. |

### Registries in the dashboard

The dashboard (DS001) has a Registries tab and a Registry selector in the Add model form, both built on the five registry tools. The tab and the module that holds its logic and markup helpers are `local-llm-dashboard-registries.js`, beside the dashboard; the Add form's lookup and entry building use the settings model (`local-llm-settings-model.js`).

| Element | Behaviour |
| --- | --- |
| Registries tab | Lists `local_llm_registry_list`: label, kind, URL, enabled, credential state (`set`, none or `unreadable`) and the models that use it. An administrator adds a registry and edits one they added (`id`, `kind`, `url`, `label`, `authOrigins`; the id and kind are fixed once it exists), enables or disables any registry but `huggingface`, and removes one they added. `huggingface` has no actions. A built-in other than `huggingface` can be enabled, disabled and given a credential only. |
| Credential form | Set credential uses a password input that is empty each time the form opens, is never filled by the page, and is emptied before the credential call starts, so a slow or failed call leaves nothing in the page. The token goes only into the `local_llm_registry_credential_set` call: it is not kept on the dashboard, not shown and not repeated in a message. The user name field is offered for `oci` registries only. When `credentialStorage.available` is `false`, Set credential is disabled with the reason, and stays disabled after the dashboard's busy lock ends. Clear credential calls `local_llm_registry_credential_clear`. |
| Registry selector | Offers the enabled registries whose `formats` contain the Source kind's format (`gguf` for a GGUF file, `hf`, `exl3`); an Ollama tag has none. A registry that stops qualifying (disabled, or an OCI registry after the kind changes to EXL3) gives way to Hugging Face and the lookup is forgotten. Before the list has arrived only Hugging Face is offered. |
| Field labels | For an `oci` registry the Revision field is the Tag (default `latest`), the repository is an OCI repository such as `ai/smollm2`, and the GGUF file is optional. Other kinds keep Revision and the required file. |
| Lookup and entry | The lookup sends `registry` unless it is `huggingface`. `modelEntryFromForm` names the `registry` in a `huggingface` or `hf-snapshot` source for a mirror or ModelScope, and builds `oci` (GGUF) and `oci-snapshot` sources for an `oci` registry, with `repository` and `tag`. Sizing keeps its source: `gguf-header` fits `oci`, `config.json` fits `oci-snapshot`. |
| Carry rule | The commit a lookup read, or the `manifestDigest` of an OCI lookup, goes into the entry only while the form still names what the lookup read: the registry, the repository, the revision or tag and, for a GGUF lookup, the file. Any change sends the typed revision or tag, which the agent pins at Add. |

### Deployment state machine

```
idle ──run──▶ downloading ──▶ verifying ──▶ starting ──▶ loading ──▶ ready
  ▲              │ cancel / drain                                  │ stop
  │              ▼                                                  ▼
  └──────────  paused  ◀── restart ──                           stopping ──▶ idle
any phase ── failure ──▶ error (the next run or stop clears it; stop also clears paused)
```

One deployment exists at a time. A second `run` while one is active is rejected with `busy` unless `replace: true`. A repeated `run` with the same `requestId` is a no-op, so a client retry cannot start a second job. Before the download and again before the runner starts, admission (DS003) is evaluated against the current hardware snapshot.

The job takes an immutable copy of the model source when it starts. A registry edit during a download cannot change which file is fetched. Deleting the weights of, updating, or removing a model in use is rejected with `in_use`. Ollama tags can share blobs. Deleting one tag's weights never removes a partial blob that another tag's recorded pull claims, and it is rejected with `in_use` while another tag's running pull has reported a blob this deletion would touch. While any other Ollama pull runs, partials that no tag claims are kept, because that pull may not have reported them yet.

### Restart

State is written atomically to `/data/state/controller.json`. After a restart, `downloading`, `verifying` and `pulling` become `paused`, and `starting`, `loading`, `ready` and `stopping` become `idle`, because the runner process did not survive. Nothing resumes automatically; the next explicit Run resumes a paused download with `Range`.

### Reuse from repository DS008

The retired repository specification is kept at commit [`03697765`](https://github.com/AssistOS-AI/local-llms/blob/03697765a35d92adf4c7db1be9616c0b5a64cb63/docs/specs/DS008-model-lifecycle.md); the table records what local-llm took from it.

| DS008 rule | local-llm |
| --- | --- |
| Catalog is read-only; registry is operator-created and persists on the volume | Kept |
| Registration records metadata only | Kept: `model_add` stores metadata and never downloads |
| Registry writes are atomic | Kept (write to a temporary file, then rename) |
| Download is built into start; llama.cpp models must be pre-placed | Replaced: explicit Run downloads, resumes and verifies |
| Switching models needs an agent restart | Replaced: Run with `replace: true` stops the current runner and starts the new one |

### Rationale

#### Explicit download resumption

A restart can be the operator's way of stopping a large download, and an automatic resume would consume bandwidth and disk without a request. The state records `paused` with the byte count, and the next Run continues from there.

Weights move onto the disk only after an explicit Run, are verified against a pinned identity, survive restarts as resumable partials, and are removed only by an explicit delete.

### Venus metadata and export compatibility

Catalog v4 separates recommendation and measurement keys from eligibility. Eligibility remains dedicated, unified and cpu; venus uses CPU eligibility and vulkan uses dedicated eligibility. Metadata accepts dedicated, unified, cpu and venus only. A v3 envelope accepts only the original three metadata profiles, so relabelling Venus entries as v3 is invalid. State remains version 1. Unrelated state saves preserve raw registry entries, including entries hidden as unsupported. Add and Update validate with seed:false before pinning, regardless of an input seed flag. User aliases do not inherit seed certification.

The Venus recommendation accepts only llama.cpp-vulkan and partial ctxSize 512–131072, parallel 1–4 and loadMode auto or none. Explicit parameters, including an empty object, replace the saved parameter set; request values override the recommendation, which overrides the runner defaults. With no explicit parameters, a valid saved set is used. Invalid saved values fall back with the existing one-time log. Verified training-context changes still renormalize from the original requested/saved pair and repeat admission.

validated.venus accepts only llama.cpp-vulkan with 1–16 unique local-llm.venus-measurement/v1 records. Empty profile maps remain non-certifying. Each record has id, UTC measuredAt, evidence with runId, manifestSha256 and an opaque plain-text reference, the complete matching pinned GGUF modelSource including ordered shards, and configuration with all three params, resolvedThreads, hostChip, hostRamBytes, vmCpus and vmRamBytes. Unknown properties, unsafe integers, invalid timestamps, source mismatches and duplicate IDs are refused. Only the shipped or operator-selected trusted seed may carry records. The seed curator verifies the scoped evidence externally; the agent fetches or executes no reference.

The evidence digest identifies a final immutable evidence index. That index binds a separately frozen execution manifest and all required trial, review, settlement, cleanup and restoration receipts by path and hash, excluding its own hash. An incomplete or failed index cannot qualify as a successful measurement. Later evidence requires a new retained index and explicit metadata update.

The pure exportModelMetadata(models,{seed,targetSchema,dropVenusMetadata}) helper in src/controller/venusMetadata.mjs defaults to v4, validates under explicit trust context, clones entries and strips internal seed flags. v3 export rejects any recommended.venus or validated.venus branch with catalog_downgrade_lossy and exact loss paths. Only dropVenusMetadata:true permits removing those whole branches, returned separately as dropped. Sources, eligibility and legacy records remain unchanged. No metadata is relabelled. Unknown target versions are refused.

For an offline seed export from the repository root, use:

```sh
node --input-type=module -e 'import fs from "node:fs"; import { exportModelMetadata } from "./local-llm/src/controller/venusMetadata.mjs"; const input=JSON.parse(fs.readFileSync(process.argv[1],"utf8")); const {schema,models,dropped}=exportModelMetadata(input.models,{seed:true,targetSchema:"local-llm.catalog/v3",dropVenusMetadata:true}); process.stdout.write(JSON.stringify({schema,models},null,2)+"\n"); process.stderr.write(JSON.stringify({dropped})+"\n");' catalog-input.json > catalog-v3.json 2> catalog-losses.json
```

For registry export, pass seed:false and an array of entries. Applying the returned models to backed-up state is a separate operator action. Old agents reject v4 seed envelopes, so downgrade needs their matching shipped v3 seed or a reviewed v3 export. Older readers may hide Venus-bearing registry entries but preserve their raw objects during unrelated saves, allowing visibility after upgrade.
